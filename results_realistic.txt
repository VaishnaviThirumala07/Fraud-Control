Interpretation
----------------
This is the clearest evidence that the original model's near-perfect
score was driven by post-transaction balance leakage, not real
predictive signal:

- ROC-AUC barely moves (0.9998 -> 0.9995) because AUC is
  threshold-independent, and "fraud only happens in TRANSFER/CASH_OUT"
  alone already separates most of the space.
- But PRECISION collapses (97.4% -> 20.6%) because, without knowing
  whether the sender's account ended up drained, the model can no
  longer distinguish fraudulent TRANSFER/CASH_OUT transactions from
  the much larger pool of legitimate ones of the same type. At a fixed
  0.5 threshold this produces 6,244 false alarms instead of 44.
- RECALL stays high (98.4%) because transaction type alone (fraud is
  never CASH_IN/PAYMENT/DEBIT) already rules out ~74% of transactions,
  so the model rarely misses actual fraud -- it just also flags many
  innocent TRANSFER/CASH_OUT transactions alongside it.

Practical takeaway: a real-time fraud-prevention system built on these
pre-transaction fields alone would need a much better feature set
(e.g. account history, velocity/frequency features, device/IP signals)
to be usable -- flagging 1 in 5 alerts as real fraud is not
operationally deployable. The original "99.99% accuracy" model is only
valid for offline/retrospective fraud labeling where post-transaction
balances are already known, not for blocking transactions in real time.
